# 偵察：查現況，寫草稿，走人

**你是偵察，不是動工。** 這一輪的產出是**一批草稿檔**，不是一行 code，也不是 issue。

⚠️ **你不開 issue、不查重、不改任何檔案（除了自己那份草稿）。** 對外的動作全部由總管理做 ——
N 個偵察平行跑的時候互相看不見，各自查重、各自開，同一批裡的重複擋不住。理由見 [ADR-0006](../../docs/adr/0006-recon-writes-a-draft-not-an-issue.md)。

一件事一個 worker，平行跑。說「分析」就會自己 fan out —— 不需要有人告訴你開幾個。

> **架構與規則**：[`docs/fleet-flow.md`](../../docs/fleet-flow.md)；**某條規則當初為什麼這樣定**：[`docs/adr/`](../../docs/adr/)。
> 改執行規則改這份 SKILL.md，改判斷邊界改 fleet-flow。

> 📁 **路徑假設**：`~/code/` 底下是兄弟目錄（`work-helper`、`work-docs`、各專案 repo）。
> 這台機器不是這樣擺的話 `ls ~/code` 看一眼，還是找不到就問使用者，不要猜。

## 每個 worker 做四件事

### 1. 讀目標 repo 的開 issue 規範

照**你所在 repo 的 `CLAUDE.md` 觸發表**找到 issue 規範並讀完。issue body 長什麼樣由那份決定，不由這支 skill 決定。

**完成條件**：你講得出那份規範要求哪些欄位。講不出來就是還沒讀。

### 2. 查現況

grep、讀檔、必要時開自己的 worker 去別的 repo 查（**只帶結論回來，不要把對面的 repo 搬進 context**）。

**完成條件**：你手上有「要改哪些檔案」和「怎麼驗」。少任何一個就是還沒查完，回去查。

### 3. 寫草稿檔

```bash
mkdir -p ~/code/work-helper/drafts/$(date +%F)
# 寫進 ~/code/work-helper/drafts/<日期>/<短名>.md
```

`drafts/` 被 `.gitignore` 忽略，不進版控。草稿內容 ＝ 未來那張 issue 的 body，
所以格式照步驟 1 那份規範。有 Slack 來源時第一行必須是可見指紋，第二行再寫類型
（`Bug` / `Feature` / `Task`）；沒有指紋時第一行才寫類型。

⚠️ **一份草稿一個問題。** 單位是**一個問題**，不是一個模組、也不是你這次調查的產出。
把 N 個發現塞成一份，會生出讀起來像 spec 的東西 —— 使用者得整份重寫。
一次調查查出 3 件不相干的事，就寫 3 份草稿。

**外加四件**：

1. **指紋放第一行**（如果有）—— Slack 來源就是 `Rec…` record_id，要看得見，
   不要藏在 HTML 註解裡。PM 口述、順手發現的**沒有指紋**，那就寫一行
   「來源：…，建議用關鍵字 X 查重」給總管理。
2. **「要改哪些檔案」獨立成一段** —— 總管理要拿它算這一批之間有沒有交集。
3. 最後一行自己標 `✅ 可以發布`、`⚠️ 範圍未定` 或 `⚠️ 做法未定`
4. 標 `⚠️` 的，把**推導**（考慮過 A/B、為什麼排除 A）寫進草稿最後一節 ——
   你交完就不在了，推導沒有第二次被問出來的機會。

**完成條件**：草稿寫好，而且裡面的每個路徑 `git cat-file -e origin/<主分支>:<path>` 過、
每個識別字 grep 得到。錨點錯掉的草稿跟程式碼寫錯同一個等級。

### 4. 交件，然後停

**草稿寫完就結束。回覆只給一行路徑。**

**完成條件**：你的回覆是一行 `drafts/…/….md`。**不要把草稿內容貼回來**，也不要摘要、
不要「接下來我要…」—— 回傳值會進總管理的 context，N 份 body 穿過去等於又壓成一個 session。

## `✅` / `⚠️` 怎麼標

你在標的是**這份草稿能不能直接變成任務** —— 使用者看完會決定它開成 issue（掛 `ready-for-agent`），
還是當天直接派工做掉、不開 issue。

| 草稿的狀態 | 標 |
| --- | --- |
| 每一格都填滿了：改動點列得完、怎樣算解完寫清楚 | `✅ 可以發布` |
| 缺「方向」那格，而且**答案會改變要開幾個任務、或會改變動到哪些檔案** | `⚠️ 範圍未定` |
| 缺「方向」那格，但**範圍不變**，只是實作走法還沒挑 | `⚠️ 做法未定` |

兩種 `⚠️` 都要指名缺的是哪一格、列出你考慮過的做法。

**為什麼要分**：`⚠️ 範圍未定` 使用者得在**發布前**談完 —— 顆粒度定的是 slug，
開了 issue 編號就定死了。`⚠️ 做法未定` 可以直接開 issue，接單的 agent 會跟他談。
**分不出來就標 `⚠️ 範圍未定`**（保守的那邊，代價只是早一點談）。

⚠️ **查不完不是 `⚠️`，是還沒交件。** 「我沒去查後端」→ 回去查。
`⚠️` 專指「**使用者答了會改變做法**」的缺口 —— 你查再久也不會冒出答案。

這個標籤是使用者唯一會 review 的東西。標錯了他馬上知道你沒搞懂，代價是兩分鐘；標對了他兩分鐘就能決定出口。

## Context 邊界：只拿 repo 外的東西

| | 拿不拿 |
| --- | --- |
| 模組路徑、相關檔案在哪 | ❌ repo 自己的 `CLAUDE.md` 就是地圖，自動載入 |
| 別的 repo 在哪 | ❌ 登記在 `~/code/CLAUDE.md` |
| PM 需求文件、prototype、UI 稿 | ✅ **repo 外的東西，只有這種要別人給** |
| 使用者猜問題在哪 | ❌ 那是你要查的，先接受會把你錨定在錯的地方 |

## 收工前：工作區要乾淨

N 個 worker 共用同一份 checkout，所以：

```bash
git -C <checkout> status --short
```

**空的才算收工。** 不是空的表示有人越界動了檔案 —— 那段時間寫的草稿，錨點要重驗（`file:line` 可能指向未提交的狀態），而且其他 worker 可能讀到改一半的檔案、寫出錯的結論。

⚠️ 這件事發生過：使用者回頭在偵察的 pane 裡下了實作指令，4 個檔案被改掉，而另外 4 個 worker 正在讀同一份工作區。**共用 checkout 只拿來偵察，要改檔案就開 worktree。**

---

## 這一輪**不**做的事

- **不開 worktree、不開 branch。** worktree 要 branch 名 → 要 issue 編號 → issue 還沒開，是循環。
- **不實作。** 就算你已經知道怎麼改也不要動手 —— 實作走 `fleet-worktree`，在自己的 worktree 裡。
- **不 grill 使用者。** 有要人決定的事就標 `⚠️` 寫進草稿，然後交件。N 個 worker 每個都想討論，就是一整天沒了。
