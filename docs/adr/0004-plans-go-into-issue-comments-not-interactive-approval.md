# 計畫寫進 issue comment，不用 plan mode 的互動核可

接單的 agent 先把實作計畫 comment 回 issue，然後停；你批次看完才放行。
不用 Claude Code plan mode 那種「跳出來等你按同意」。

| | 互動核可 | 計畫進 issue comment |
| --- | --- | --- |
| 你被打斷幾次 | **N 次**，隨機 | **0 次** |
| 怎麼看 | 一次一個，被迫切 context | 坐下來一次看 N 份 |
| 三天後查得到嗎 | ❌ 只在 terminal | ✅ 在 issue 上 |

3–6 個任務的話，批次看是一個 5–10 分鐘的區塊。

## 為什麼每個都看，不篩

想過用「四個性質」篩（只審 bounded 掉的），否決了：判斷「這個需不需要審」本身就要花時間去想，
還會漏判，而那個成本跟直接掃一眼計畫差不多。不用篩，因為**成本自動隨複雜度縮放** ——
簡單的計畫 3 行、10 秒放行；複雜的 20 行、2 分鐘，而那正是該花的時候。

門檻要低：你看的是「**它有沒有理解對**」，不是「這是最好的做法嗎」。
理解對就放行，不然這關會變成新的瓶頸。

## 這關不能被 issue 取代

issue 說的是**改哪些檔案**（任務的邊界），計畫說的是**怎麼改**（做法）。
方向對、範圍對，做法照樣可以歪。

> 業界把這叫 plan approval pattern：review 一次整條軌跡，比核可十個片段便宜又安全。
